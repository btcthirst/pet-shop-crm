# pet-shop-crm

Внутрішня CRM зоомагазину: каталог товарів, залишки на складі, клієнти, замовлення та дві ролі користувачів (Admin / Manager).

Розробка ведеться за технічною специфікацією `pet-shop-crm — технічна специфікація.md`.

**Стан: етап 6 (дашборд).** Готово: авторизація з ролями Admin / Manager (етап 1), каталог категорій і товарів (етап 2), склад — прихід, коригування, журнал рухів і підсвітка малих залишків (етап 3), клієнти — список, картка з нормалізованими телефонами та історією (етап 4), замовлення — створення з позиціями, транзакційне списання, переходи статусів і скасування (етап 5), дашборд із новими замовленнями й товарами з малим залишком (етап 6). Далі: E2E-тести, фінальне README, скриншоти й деплой (етап 7).

## Запуск

```bash
nvm use                    # Node 24 з .nvmrc
pnpm install
cp .env.example .env       # заповнити рядки Neon та AUTH_SECRET
pnpm db:migrate            # застосувати міграції
pnpm db:seed               # демо-дані (етап 1)
pnpm dev                   # http://localhost:3000
```

### Змінні середовища

| Змінна             | Призначення                                               |
| ------------------ | --------------------------------------------------------- |
| `DATABASE_URL`     | pooled-рядок Neon (хост містить `-pooler`) для застосунку |
| `DIRECT_URL`       | прямий рядок Neon для Prisma CLI (міграції, seed, studio) |
| `DATABASE_URL_DEV` | те саме для гілки `dev` Neon — локальна розробка          |
| `DIRECT_URL_DEV`   | те саме для гілки `dev` Neon — міграції під час розробки  |
| `AUTH_SECRET`      | `openssl rand -base64 32`                                 |

Локально `DATABASE_URL_DEV` / `DIRECT_URL_DEV` мають пріоритет над основними (див. `src/lib/env.ts` і `prisma.config.ts`), тому розробка не зачіпає демо-дані. На Vercel і в CI змінних `*_DEV` немає — там використовується основна база. Щоб застосувати міграції до основної гілки вручну: `DIRECT_URL=<прямий рядок> pnpm db:deploy`.

`.env` у `.gitignore`, у репозиторії лише `.env.example`.

## Схема БД

Моделі: `User`, `Category`, `Product`, `StockMovement`, `Customer`, `Order`, `OrderItem`, `OrderStatusHistory`. Гроші зберігаються в копійках (`priceKopecks`, `unitPriceKopecks`, `totalKopecks`). Повний опис — у `prisma/schema.prisma`.

Окрім схеми Prisma застосовуються CHECK-обмеження (`prisma/migrations/*_constraints`):

- `Product.stock >= 0`
- `Product.priceKopecks >= 0`
- `OrderItem.quantity > 0`

## Каталог (етап 2)

| Сторінка         | Можливості                                                                  |
| ---------------- | --------------------------------------------------------------------------- |
| `/products`      | пошук `q`, фільтри `categoryId` і `lowStock`, пагінація `page` / `pageSize` |
| `/products/new`  | створення товару (Admin); Manager бачить «Доступ заборонено»                |
| `/products/[id]` | картка товару, редагування й деактивація/активація (Admin)                  |
| `/categories`    | список із кількістю товарів, створення, перейменування, видалення (Admin)   |

| Endpoint               | Методи                   | Права                |
| ---------------------- | ------------------------ | -------------------- |
| `/api/products`        | `GET`, `POST`            | A: `POST`            |
| `/api/products/[id]`   | `GET`, `PATCH`, `DELETE` | A: `PATCH`, `DELETE` |
| `/api/categories`      | `GET`, `POST`            | A: `POST`            |
| `/api/categories/[id]` | `PATCH`, `DELETE`        | A                    |

Правила домену:

- Ціни в API — цілими копійками (`priceKopecks`); форма приймає гривні (`249.90`) і конвертує.
- `sku` унікальний і обрізається від пробілів; дублікат → `400 VALIDATION_ERROR`.
- `slug` категорії генерується з українського тексту (`toSlug`) і оновлюється при перейменуванні.
- Товар не видаляється фізично: `DELETE` лише деактивує (`isActive = false`), замовлені позиції не зникають.
- Категорію, до якої належать товари, видалити не можна (`400`), кількість товарів показується в списку.
- `stock` не змінюється через `Product` — лише рухами `StockMovement` (етап 3).
- Фільтр «мало на складі» — це `stock <= lowStockThreshold`, критерій не виражається типізованим `where` Prisma, тому список береться raw SQL (`Prisma.sql`) з безпечною parameterization.

## Склад (етап 3)

| Сторінка | Можливості                                                                                                          |
| -------- | ------------------------------------------------------------------------------------------------------------------- |
| `/stock` | залишки з підсвіткою малих, форма приходу/коригування, журнал рухів з фільтрами `productId` і `reason` і пагінацією |

| Endpoint               | Методи | Права                          |
| ---------------------- | ------ | ------------------------------ |
| `/api/stock/movements` | `GET`  | A, M                           |
| `/api/stock/movements` | `POST` | RESTOCK — A, M; CORRECTION — A |

Правила домену:

- `delta` знаковий: додатнє — прихід, від'ємне — списання; нульова дельта відхиляється (`400`), адже журнал без зміни залишку нічого не пояснює.
- Прихід може бути лише додатковим; зменшити залишок можна лише `CORRECTION`, а це вже право Admin. Правило однакове для API і для форми (`toStockMovementInput`), тому через UI його не обійти.
- Залишок змінюється умовним `updateMany` (`stock >= |delta|`), а рух пишеться в тій самій транзакції — паралельні записи не загонять товар у мінус, а журнал не може розійтися із залишком.
- `sum(delta) за товаром === stock` — інваріант перевіряється вручну; `pnpm db:seed` теж пише баланс рухом (`CORRECTION`), тому інваріант тримається і на демо-даних.
- Причина `ORDER` / `CANCEL` з API не приймається: ці рухи пише лише замовлення (етап 5).
- Недостатній залишок → `409 INSUFFICIENT_STOCK` з `details.available` і `details.requested`; невідомий товар → `404`.
- Авторизація перевіряється **перед** валідацією тіла, тож анонімний клієнт отримує `401`, а не підказки про правила payload у `400`.

## Клієнти (етап 4)

| Сторінка          | Можливості                                                               |
| ----------------- | ------------------------------------------------------------------------ |
| `/customers`      | список з пошуком за ім'ям і телефоном, лічильником замовлень, пагінацією |
| `/customers/new`  | створення клієнта (Admin і Manager)                                      |
| `/customers/[id]` | картка: редагування, історія замовлень, видалення (лише Admin)           |

| Endpoint              | Методи         | Права |
| --------------------- | -------------- | ----- |
| `/api/customers`      | `GET`, `POST`  | A, M  |
| `/api/customers/[id]` | `GET`, `PATCH` | A, M  |
| `/api/customers/[id]` | `DELETE`       | A     |

Правила домену:

- Телефон нормалізується в E.164 перед записом (`normalizePhone`): національні форми `0501234567` і `501234567` стають `+380…`, `00…` і явний `+` зберігають код країни, а `+` без коректного коду або надто короткі номери відхиляються (`400`). `phone` унікальний, тому дубль → `400` з `details.field: "phone"`.
- Правило нормалізації живе в `src/lib/phone.ts`, а не в Zod-схемі: API, Server Action і форма використовують одну реалізацію через `customerInputSchema` / `customerFormSchema`.
- Email необов'язковий; порожній рядок перетворюється на `null`, некоректний email → `400`.
- Видалення клієнта дозволено лише коли в нього немає замовлень: інакше `400 VALIDATION_ERROR` з `details.ordersCount`. Перевірка і видалення — у сервісі, кнопка показується лише Admin.
- Картка показує історію замовлень (номер, дата, статус, сума) з окремим станом «замовлень ще немає».
- Авторизація перевіряється **перед** валідацією тіла — анонімний запит отримує `401`, а не підказки про payload у `400`.

## Замовлення (етап 5)

| Сторінка       | Можливості                                                  |
| -------------- | ----------------------------------------------------------- |
| `/orders`      | список із фільтрами за статусом і клієнтом, пагінацією      |
| `/orders/new`  | створення замовлення з позиціями (Admin і Manager)          |
| `/orders/[id]` | позиції, сума, клієнт, історія статусів і доступні переходи |

| Endpoint                  | Метод         | Права |
| ------------------------- | ------------- | ----- |
| `/api/orders`             | `GET`, `POST` | A, M  |
| `/api/orders/[id]`        | `GET`         | A, M  |
| `/api/orders/[id]/status` | `POST`        | A, M  |

Правила домену:

- Замовлення створюється однією транзакцією: залишки списуються умовним `updateMany({ stock: { gte: quantity } })`, для кожної позиції пишеться рух `ORDER` з від'ємним `delta`, а перший запис історії має `fromStatus: null`. Якщо хоч одна позиція не пройшла, транзакція відкочується — замовлення, рухи й залишок не змінюються (`409 INSUFFICIENT_STOCK`).
- Паралельні замовлення на останню одиницю: умовний `updateMany` перевірено тестом — успішним буде рівно одне замовлення, друге отримає `INSUFFICIENT_STOCK`.
- `unitPriceKopecks` копіюється з товару, `totalKopecks` рахується на сервері через `sumOrderItems`, тож зміна ціни не впливає на старі замовлення, а `totalKopecks` з payload ігнорується (схема його не приймає).
- Деактивовані товари не можна замовляти (`400`), невідомий товар або клієнт — `404`.
- Переходи статусів описані лише в `features/orders/status.ts`: UI показує дозволені кнопки, сервіс перевіряє перехід і разом зі зміною статусу пише `OrderStatusHistory`. Заборонений перехід — `409 INVALID_TRANSITION` з `details.fromStatus` / `details.toStatus`.
- Скасування повертає позиції на склад рухами `CANCEL` (додатний `delta`) у тій самій транзакції, тому `sum(delta) === stock` тримається завжди. Кінцеві статуси `DELIVERED` і `CANCELLED` переходів не мають.

### Тести

- `tests/unit/orders.test.ts`: повна матриця переходів (усі дозволені й усі заборонені, включно з поверненнями назад і «теми самим» статусом), схеми замовлення, підрахунок суми, розбір `FormData` із позиціями.
- `tests/integration/orders.test.ts`: списання залишку і рухи `ORDER`, недостатній залишок без змін у БД, скасування з рухами `CANCEL`, невідомий товар/клієнт, деактивований товар, два паралельні замовлення на останню одиницю (успішне рівно одне), ланцюг `NEW → CONFIRMED → SHIPPED → DELIVERED`, `403` для Manager на `PATCH /api/products/:id` та інваріант `sum(delta) === stock`.
- Інтеграційні тести працюють на dev-базі (у CI — на Postgres service container) і прибирають за собою категорію, товари, клієнта та користувача-автора. Автора створює сам тест, тому seed не потрібен. `.env` для Vitest підвантажує `tests/setup-env.ts`.

## Дашборд (етап 6)

| Endpoint         | Метод | Права |
| ---------------- | ----- | ----- |
| `/api/dashboard` | `GET` | A, M  |

- `src/features/dashboard/service.ts` віддає два блоки: незакриті замовлення (`NEW` і `CONFIRMED`) і активні товари з малим залишком. Обидва рахуються тим самим запитом, що й таблиця на екрані, тож лічильник завжди збігається з вмістом.
- Критерій малого залишку той самий, що в каталозі, — `stock <= lowStockThreshold`, але лише для `isActive = true`: деактивований товар не чекає приходу, тож не піднімає тривогу. Тому фільтр лишається в сирому SQL, як і в `products/service.ts`.
- Порядок показу: замовлення — від найновіших, товари — від найменшого залишку.
- Ендпоінт захищено `requireRole("ADMIN", "MANAGER")`, бо він читає кілька доменів одночасно, і всі ролі, які можуть увійти, мають право на ці дані.

### Тести

- `tests/integration/dashboard.test.ts` не порівнює числа з «магіними» значеннями, а з окремими запитами до БД: кількість незакритих замовлень, правило малого залишку, складка за `sku`, сортування за залишком, ліміт рядків і прихована деактивна позиція. Це і є критерій етапу «дані відповідають БД».
- `vitest.config.mts`: `fileParallelism: false` (інтеграційні файли спільно використовують одну БД, тому глобальний підрахунок міг би змагатися з фікстурою сусіднього файлу) і `testTimeout: 30_000` (багато послідовних round-trip'ів до віддаленого Neon).

## Авторизація

- Сесія — JWT (Auth.js Credentials), паролі звіряються через bcryptjs (cost 12) у `src/lib/auth.ts`.
- `src/proxy.ts` (Next 16 замість middleware) не пропускає анонімних відвідувачів до сторінок і відправляє їх на `/login?callbackUrl=...`; `api` виключено, щоб Route Handlers відповідали JSON-контрактом помилок.
- Права перевіряються на сервері: `requireRole()` / `requirePermission()` у `src/lib/permissions.ts`. Приховування посилання в навігації — лише зручність.
- `GET /api/users` повертає `401` без сесії та `403` (`{"error":{"code":"FORBIDDEN",...}}`) для Manager.

## CI

`.github/workflows/ci.yml`: `pnpm install --frozen-lockfile` → `lint` → `typecheck` → `db:deploy` (Postgres 16 як service container) → `test` → `build`.

`typecheck` спершу виконує `prisma generate`, бо згенерований клієнт не потрапляє в git — свіжий клон і CI проходять перевірку без ручного кроку.

## Відхилення від специфікації

Специфікація була написана до сучасних мажорних версій бібліотек. Що змінилося:

- **Prisma 7**: генератор `prisma-client-js` deprecated → `prisma-client` з обов'язковим `output` (`src/generated/prisma`). Рядки підключення переїхали з `datasource` у `prisma.config.ts` (`DIRECT_URL` з fallback на `DATABASE_URL`), `url`/`directUrl` у схемі більше не задаються. Клієнт створюється через driver adapter `@prisma/adapter-pg`. Seed задається у `prisma.config.ts`, а не в `package.json`; `migrate dev` більше не запускає seed і generate автоматично. Початкова міграція згенерована офлайн через `prisma migrate diff --from-empty --to-schema` (секрети/БД не потрібні).
- **pnpm 12**: `onlyBuiltDependencies` замінено на `allowBuilds` у `pnpm-workspace.yaml` (`prisma`, `@prisma/engines`, `esbuild`, `@tailwindcss/oxide`, `sharp`, `unrs-resolver`). Старе поле вже ігнорується з pnpm 11.
- **Next.js 16 + Tailwind 4**: Turbopack за замовчуванням, shadcn/ui ініціалізовано в новому CLI (`style: radix-nova`).
- **bcryptjs 3** має власні типи, тому `@types/bcryptjs` не встановлювався.
- **Next.js 16**: middleware перейменовано на proxy (`src/proxy.ts` з named export `proxy`); Auth.js-проміс обгорнуто функцією, бо Next розпізнає лише статично аналізовні експорти. `next-auth@5.0.0-beta.32` експортує `NextAuth` як default, а JWT-тип не можна розширити через `next-auth/jwt` (тільки re-export з `@auth/core`, недоступного для pnpm) — форма токена описана в `src/lib/auth.config.ts`.
- **`"use server"`**: файл може експортувати лише async-функції, тому стан логіну не експортується константою.

## План

Етапи 1–7 — авторизація, каталог, склад, клієнти, замовлення, дашборд, тести й деплой — за планом розділу 13 специфікації.
